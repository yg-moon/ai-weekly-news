# RUNBOOK_WEEKLY

**매주 무엇을 어떻게 실행하는가.** 대상 주를 정하는 것부터 수집·선별·집필·발행까지의 절차 전부를 담는다. 주간 발행 작업은 이 문서에서 시작해 여기서 가리키는 문서까지 읽으면 끝난다.

## 왜 이 문서가 기준인가

- 스케줄러에 저장된 프롬프트는 보통 그 서비스의 서버에 있어 git 밖이다. 거기에 사양을 쓰면 버전 관리도 되돌리기도 안 된다.
- 프롬프트는 짧은 포인터로 고정하고 실제 사양은 저장소 안에 둔다. 어긋나면 이 문서가 맞다. 절차를 바꿀 때는 이 파일을 고친다.

## 실행 절차

**수집과 선별을 위임하지 않는다.** 하위 에이전트나 다른 모델에 넘기면 원문 대조가 느슨해진다. 부득이하게 위임한다면 메인 세션과 같은 모델을 명시적으로 지정하고 기본값에 맡기지 않는다.

### 0. 먼저 읽는다

클론에 들어 있어도 열지 않으면 없는 것과 같다. 아래 둘을 읽어야 판단 기준이 갖춰진다.

- [`../AGENTS.md`](../AGENTS.md) 의 **문서 작성 규칙** — 문체 규칙은 저장소 문서와 발행물에 똑같이 적용된다. 10절은 여기에 발행물용을 더한 것이다.
- [`INTENT.md`](INTENT.md) 의 **품질 기준** — 절차가 답하지 않는 지점은 이 기준으로 판단한다.

아래 명령은 모두 저장소 루트에서 실행한다.

### 1. 대상 주 확정

대상은 **직전에 완결된 ISO 주(월요일부터 일요일까지)**다. 실행 환경이 UTC라도 반드시 KST로 계산한다. 아래 명령은 어느 요일에 실행해도 맞다. 일요일 밤에 돌리면 아직 안 끝난 이번 주가 아니라 지난주가 나온다.

```bash
SUN=$(TZ=Asia/Seoul date -d 'last sunday' '+%Y-%m-%d')    # 대상 주 일요일
MON=$(TZ=Asia/Seoul date -d "$SUN - 6 days" '+%Y-%m-%d')  # 대상 주 월요일
WEEK=$(date -d "$MON" '+%G-W%V')                          # 예: 2026-W36
```

- `%G-W%V`는 ISO 연도와 주차라 연말 경계에서도 어긋나지 않는다. 2027년 1월 4일에 실행하면 `2026-W53`이 나온다. `%Y`를 쓰지 않는다.
- GNU date에서 `'2026-09-13 23:00 - 7 days'`처럼 시각 뒤에 `-`를 쓰면 시간대 오프셋으로 오독한다. 상대 표현은 위처럼 쓴다.
- `content/week/<WEEK>.md`가 이미 있으면 그 주는 발행된 것이다. 덮어쓰지 말고 주간호 작성을 건너뛴다. **그래도 15절의 분기 판정은 거친다.** 주간호가 이미 있는 것과 분기호가 있는 것은 별개다.
- 주차를 지정받으면 위 계산 대신 그 주차를 대상으로 삼는다. 과거 주차 백필이 이 경우다. 나머지 절차는 같다.
- 주차를 지정받았을 때는 월요일과 일요일을 아래로 구한다. `date -d` 가 없는 맥에서도 돈다.

```bash
read MON SUN < <(node -e 'const [y,w]=process.argv[1].split("-W").map(Number),j=Date.UTC(y,0,4),m=j-((new Date(j).getUTCDay()+6)%7)*864e5+(w-1)*7*864e5,d=(t)=>new Date(t).toISOString().slice(0,10);console.log(d(m),d(m+6*864e5))' "$WEEK")
```

### 2. 후보 풀 — 헤드라인을 먼저 전부 읽는다

**검색으로 시작하지 않는다.** 검색은 검색어가 결과를 정한다. 경제 용어로 찾으면 경제 뉴스만 나오고, 그 주의 진짜 큰 뉴스는 후보에 들어오지도 못한다.

대상 주의 헤드라인을 날짜별로 통째로 받아서 읽는 것부터 시작한다.

**분야별로 파일에 받아 둔다.** 인자를 안 주면 네 소스를 다 받지만, 빈도를 뽑을 때 다시 받게 되어 같은 요청을 두 번 보낸다. 주차별 폴더에 받아 같은 기기의 다른 세션과 겹치지 않게 한다.

```bash
mkdir -p /tmp/<WEEK>
for s in domestic world tech ai; do
  node scripts/collect-headlines.mjs <대상주 월요일> <대상주 일요일> $s > /tmp/<WEEK>/$s.md
done
```

| 분야 | 출처 | 무엇을 주는가 |
|---|---|---|
| 국내 | 네이버 뉴스 랭킹 | 날짜별·주요 언론사 15곳별 많이 본 기사 5건씩 |
| 해외 | Wikipedia Portal:Current events + The Guardian 피드 | 날짜별로 분류·정리된 국제 사안과 출처 |
| AI | 연구소·기업 뉴스룸 7곳(`ai`) + Hacker News 프런트(`tech`) | 1차 발표와 날짜별 기술 화제 |

**네이버 랭킹 아카이브는 2020년 11월 중순까지다.** 그보다 앞선 날짜를 요청하면 오늘 랭킹이 대신 온다. `collect-headlines.mjs` 가 페이지의 날짜 이동 목록으로 가려내 수집 실패로 처리한다. 2020-11-15 는 밖이고 2020-11-22 는 받아진다.

**하루가 비면 경고가 stderr 로 나온다.** 정상 응답에 빈 목록이 온 적이 있어 세 번까지 다시 받는다. stdout 은 파일로 보내지므로 경고는 화면에 남는다. 경고를 보면 그 날을 다시 받아 채운다.

**날짜를 지정해 받을 수 있는 소스만 뼈대로 쓴다.** 회고형 주간지라 대상 주 7일을 정확히 덮어야 한다. 일반 뉴스 RSS는 최신 몇십 건만 담아 이 조건을 못 채운다. 실측으로 BBC World는 3.3일, Techmeme은 0.9일치뿐이었고 CNN World는 날짜가 깨져 있었다. 발행 빈도가 낮은 뉴스룸 RSS만 예외로 수 주에서 수년치를 담는다.

읽은 뒤 **같은 사안이 며칠에 걸쳐 몇 개 언론사에 반복되는지 센다.** 이것이 "그 주에 얼마나 크게 다뤄졌는가"의 측정값이다.

**셀 대상을 직접 고르지 않는다.** 머릿속에 떠오른 주제만 세면 후보를 전수로 모은 의미가 없어진다. 아래 도구로 빈도를 먼저 뽑고, 그 목록을 보고 주제로 묶는다.

```bash
node scripts/rank-topics.mjs /tmp/<WEEK>/domestic.md --top 40
```

**세 분야에 같은 기준을 적용하되 방법은 다르다.**

| 분야 | 측정 방법 |
|---|---|
| 국내 | 도구로 빈도를 뽑고 묶는다. 한글 토큰이라 잘 맞는다 |
| 해외 | 도구로 빈도를 뽑고 묶는다. 영어는 고유명사만 센다 |
| AI | **목록 전체를 읽는다.** 항목이 200여 건으로 적고 제목이 짧아 빈도가 흩어진다. 고유명사가 두 단어로 쪼개져(Hugging Face, GPT-6 Astra) 빈도에 안 잡힌다. 도구는 보조로만 쓴다 |

**'많이 본'과 '많이 보도된'은 다르다.** 네이버 랭킹은 독자 클릭 기준이라 정치 논란과 사건사고가 유리하고 재정·정책 기사가 불리하다. 랭킹에 거의 없어도 모든 신문이 1면에 올린 사안이 있다. 랭킹은 후보를 빠짐없이 찾는 도구이고, 순위는 4절 기준으로 매긴다.

### 3. 검색과 원문 대조

검색은 **후보를 만드는 데 쓰지 않고**, 헤드라인에서 고른 후보를 확인하고 보강할 때만 쓴다.

확인이 끝나면 반드시 원문을 받아 대조한다.

```bash
node scripts/read-article.mjs <URL>   # 발행일과 본문 텍스트
```

- 사실의 근거는 기사 원문뿐이다. 검색 도구가 돌려주는 산문 요약은 생성된 텍스트다.
- 수치·날짜·인용은 원문에서 확인한 것만 쓴다. 발행일이 대상 주 밖이면 그 사안의 근거로 쓰지 않고, 후속 경과 확인에만 쓴다. 본문에 넣을 때는 **그 날짜를 적는다.**
- 원문을 받을 수 없는 매체는 쓰지 않는다.
- **발표 주체의 RSS 만 열리는 경우가 있다.** OpenAI 처럼 HTML 이 막혀도 RSS 는 받아지면, 그 RSS 로 발표가 있었다는 사실과 날짜를 확인한다. 내용은 받아지는 매체로 대조한다. 출처 줄에는 1차 출처를 그대로 쓴다.

### 4. 순위

후보를 아래 순서로 비교한다. 앞의 것이 더 무겁다.

1. **그 주에 얼마나 크게 다뤄졌는가** — 며칠에 걸쳐 몇 개 언론사가 다뤘는지 헤드라인 목록에서 센다. 이 주의 가장 큰 뉴스가 1번이다.
2. **되돌리기 어려움** — 인명 피해와 집행된 결정이 무겁다. 합의와 발표가 그다음이고, 검토·발언·전망이 가장 가볍다.
3. **영향의 범위와 깊이** — 몇 명에게 닿는지와 그 사람들의 삶을 얼마나 바꾸는지를 함께 본다.
4. **축적 가치** — 1년 뒤 분기·연간 정리에서 다시 볼 사안인가.
5. **독자 근접성** — 한국 독자의 생활·일·자산에 닿는가. 해외 항목도 한국에 미치는 영향을 함께 본다.

- **분야를 고르게 배분하지 않는다.** 정치가 셋이든 경제가 넷이든 그것이 그 주의 실제 무게라면 그대로 싣는다. 억지로 나누면 5위권 밖 사안이 3위 자리를 차지한다.
- **보도 매체의 수를 검증과 혼동하지 않는다.** 1번의 "크게 다뤄졌는가"는 중요도 신호이고, 출처가 둘 이상인지는 사실 확인의 문제다. 둘은 다른 층이다.
- **계속되는 상황은 그 주의 전개로 센다.** 전쟁과 대형 재난은 몇 주에 걸쳐 보도되어 주제 단위의 빈도가 늘 높다. 1번은 그 주에 벌어진 일이 얼마나 다뤄졌는지를 센다. 주제가 몇 주째 지면에 있었는지는 다른 층이다. 그 주에 국면을 바꾼 일이 있으면 그것으로 싣고, 없으면 5절에서 빠진다. 사망자 수 갱신, 새 전선, 합의와 결렬이 국면이다.
- 정한 순서대로 번호를 매긴다. 시간순으로 늘어놓지 않는다.

**순위를 확정했으면 빠뜨린 것을 확인한다.** 고른 주제를 넘기면 상위 빈도 중 선정에 안 들어간 것을 짚어 준다.

```bash
node scripts/rank-topics.mjs /tmp/<WEEK>/domestic.md --covered "용혜인,호르무즈,종부세"
```

걸린 주제마다 뺀 이유를 댈 수 있어야 한다. 5절 게이트에 걸린 것이면 그대로 두고, 아니면 순위를 다시 본다.

### 5. 게이트

순위를 매기기 전에 거른다. 하나라도 어기면 뺀다.

- 그 주에 실제로 벌어진 일인가. 예고·전망·분석 기사는 사안이 아니다.
- 원문으로 사실을 확인했는가.
- 이미 고른 항목과 같은 사안이 아닌가. 같은 사건의 다른 측면을 국내와 해외에 나눠 실을 때는 각자 다른 내용을 다루고 서로 참조한다.
- 단발성 사건사고, 연예, 생활 기사는 뺀다. 많이 읽혔다는 것만으로는 싣지 않는다.

### 6. 작업 순서를 지킨다

헤드라인 통독 → 반복도 측정 → 게이트 → 순위 → 원문 대조 → 항목 작성 → **마지막에** 도입 문단.

- 도입 문단을 쓰려고 항목을 바꾸지 않는다. 다섯 건에 공통점이 없으면 찾지 않는다.
- 하나의 주제에 맞춰 다섯 건을 고르는 것이 이 절차에서 가장 피해야 할 실패다. 주제는 결과이지 목표가 아니다.

### 7. 매체

**주요 매체를 기준으로 삼고, 보조 매체는 주요 매체가 다루지 않은 세부를 보탤 때만 쓴다.** 헤드라인 수집도 주요 매체만 본다.

| 분야 | 주요 | 보조 |
|---|---|---|
| 국내 | 조선일보 · 중앙일보 · 동아일보 · 한겨레 · 경향신문 · 한국일보 · 서울신문 · 국민일보 · KBS · SBS · MBC · JTBC · YTN · 연합뉴스 · 연합뉴스TV (15곳) | 한국경제 · 매일경제 · 서울경제 · 이데일리 · 뉴시스 · 뉴스1 · 프레시안 · 전자신문 · ZDNet |
| 해외 | Wikipedia Current events(수집 뼈대) · The Guardian · BBC · CNN · Al Jazeera · NPR · The New York Times | CBS News · NBC News · USA Today · The Independent · Gulf News |
| AI | 연구소 1차 출처(아래) · TechCrunch · The Verge · Ars Technica | The Register · The New Stack · BNN Bloomberg · The Information · Semafor |

국내 사안은 **한국어 원문을 우선한다.** 번역을 거치지 않아 표현과 수치가 정확하고, 영문판에 없는 사안이 많다.

**AI 는 연구소 뉴스룸을 직접 추적한다.** 테크 매체 요약보다 앞서고 정확하다. `collect-headlines.mjs` 의 `ai` 소스가 아래를 날짜로 걸러 준다.

| 주체 | 경로 |
|---|---|
| OpenAI | `openai.com/news/rss.xml` |
| Anthropic | `anthropic.com/news` |
| Google AI | `blog.google/technology/ai/rss/` |
| Google DeepMind | `deepmind.google/blog/rss.xml` |
| NVIDIA | `blogs.nvidia.com/feed/` |
| Microsoft | `news.microsoft.com/source/feed/` |
| Hugging Face | `huggingface.co/blog/feed.xml` |

- OpenAI 는 HTML 페이지가 403 이지만 **RSS 는 열린다.** 10년치를 담는다.
- 뉴스룸 피드에는 고객 사례와 홍보 글이 많이 섞인다. 새 모델·연구·인수·정책 발표만 후보로 올리고 나머지는 버린다.
- 뉴스룸은 자사 발표만 담아 업계 맥락과 비판이 없다. Hacker News 프런트가 그 공백을 일부 메운다.

**도구가 거부하는 매체가 있다.** 검색 도구의 `allowed_domains` 에 연합·조선·중앙·동아·한겨레·매경·Reuters·AP·BBC·The Guardian 을 넣으면 호출 전체가 실패한다. 넣지 않는다. 다만 URL 을 알면 원문 받기는 되므로 대조에는 쓴다. Wall Street Journal 은 원문도 막혀 있다(401).

**봇 차단으로 원문을 받을 수 없는 매체가 있다.** 2026-W37 실측에 2026-09-23 실측을 더했다. 주요 매체 목록은 이 결과로 정했다.

| 받아진다 | 막힌다 |

**차단은 우회하지 않는다.** 받아지는 매체로 대조하고, 한 사안을 인용한 매체가 전부 막혔으면 그 사안은 싣지 않는다. 막힌 매체는 출처 줄에도 쓰지 않는다. 읽지 못한 원문을 근거로 내세우는 것이 된다.

**표에 없는 매체를 쓰려면 먼저 이 표에 넣는다.** 원문이 받아지는지 확인하고 주요와 보조 중 하나로 정한다. 비슷한 매체가 이미 있으면 그 층을 따른다. NBC News 는 CBS News 를 따라 보조다. 표에 없는 이름은 출처 검사가 발표 주체로 보기 때문에, 매체를 표에 안 넣으면 그 항목은 순서 검사와 주요 매체 검사에서 조용히 빠진다.

주의할 것이 하나 더 있다. 매체가 막힌 것과 **우리 추출기가 그 사이트의 마크업을 못 읽는 것**은 다르다. CNN 은 응답이 정상인데 본문이 안 잡혀 한동안 막힌 줄 알았다. 응답 코드가 200 이면 차단이 아니라 추출 문제다.

### 8. 건수는 15건으로 고정한다

**세 분야 모두 5건을 채운다.** 주차끼리 비교가 되어야 분기호와 연간호가 성립하므로 건수는 흔들지 않는다.

채우기 어려울 때 양보하는 것은 **출처의 개수**이지 사실의 확실성이 아니다.

- 복수의 독립 매체 보도를 원칙으로 한다.
- 단일 매체 보도뿐이면 싣는다. 발표 주체의 1차 출처는 독립 매체로 세지 않는다.
- 주요 매체가 당연히 보도했을 사안인데 수집 풀에 없으면 그 매체에서 먼저 찾아보고, 그래도 못 찾으면 보조 매체로 싣는다.

  국내는 네이버의 **언론사별 날짜 목록**에서 찾는다. 많이 본 랭킹에 없는 기사도 이 목록에는 다 있다. 2026-W36 물가 기사가 랭킹에는 없었고, 이 목록에는 주요 매체 다섯 곳에 있었다. 언론사 번호는 그 언론사 기사 링크의 `article/<번호>/` 부분이다. 응답은 CP949 로 인코딩되어 있다.

  ```
  https://news.naver.com/main/list.naver?mode=LPOD&mid=sec&oid=<언론사 번호>&date=<YYYYMMDD>&page=<쪽>
  ```
- **출처가 약하다는 표기는 따로 하지 않는다.** 출처 목록에 매체 이름이 그대로 나오므로 독자가 보고 판단한다.
- 어느 경우에도 **원문 대조는 건너뛰지 않는다**. 출처가 하나여도 그 하나는 반드시 읽는다.

### 9. 시점 한정

주간호는 **그 주에 알 수 있었던 것만** 담는다. 결말을 알고 쓰면 나중에 정리한 회고가 된다.

- 대상 주 이후에 벌어진 일이나 밝혀진 사실을 쓰지 않는다. 후보자가 다음 주에 사퇴했더라도 그 주간호에는 쓰지 않는다.
- 그 주에 발표된 앞으로의 계획은 쓸 수 있다. 다만 **발표 시점 기준으로** 쓴다. "9월 18일자로 폐쇄했다"가 아니라 "폐쇄하겠다고 밝혔다"이다.
- 발행일이 대상 주 밖인 기사는 사실의 근거로 쓰지 않는다. 배경 설명에만 쓰고, **본문에 그 날짜를 적어** 독자가 시점을 알게 한다. `(대상 주 밖이다)` 처럼 저장소의 용어로 표시하지 않는다. 날짜가 곧 시점이다.
- 나중에 결과가 달라져도 발행된 주간호를 고치지 않는다. 후속은 그 주가 속한 주간호에서 다룬다.

이 규칙이 있어야 주차끼리 비교가 성립하고, 분기·연간 정리가 후행 정보에 오염되지 않는다.

### 10. 문체

멋있게 들리는 문장보다 한 번에 이해되는 문장을 쓴다. [`INTENT.md`](INTENT.md) 의 품질 기준에 속한다.

**읽는 사람은 이 저장소를 모르는 외부 독자다.** 만드는 쪽의 용어와 측정값을 발행물에 쓰지 않는다. `대상 주`·`수집 풀`·`후보 풀`·`주요 매체`·`보조 매체`·`1차 출처`·`주간호` 는 전부 이 문서의 말이고, 헤드라인 반복 횟수는 무엇을 실을지 정하려고 우리가 잰 값이다. 독자는 그 절차를 모르므로 읽다가 걸린다. 시점은 날짜로, 근거는 출처 줄로 답한다.

공통 문체 규칙은 [`../AGENTS.md`](../AGENTS.md) 의 문서 작성 규칙에 있다. 아래는 발행물에만 해당한다.

- 비유는 사실을 그대로 말하는 동사가 있으면 그것으로 바꾼다.
- 수치나 고유명사로 바꿀 수 있으면 그렇게 한다. "증시를 흔들었다"보다 "코스피가 3% 내렸다"가 낫다.
- 비유는 한 항목에 최대 하나다. 도입 문단과 "왜 중요한가"에 연달아 쓰지 않는다.
- 자주 새어 나오는 표현이다. 쓰기 전에 사실로 바꿀 수 있는지 확인한다.

  관통하다 · 쏠리다 · 흔들다 · 겨누다 · 가르다 · 맞물리다 · 굳어지다 · 축을 재편하다 · 한 몸이다 · 현실화되다 · 짚다 · 지평을 열다 · 신호탄 · 분수령

- 쓴 뒤 소리 내어 읽어 본다. 무슨 뜻인지 한 번에 안 들어오면 고친다.

### 11. 항목 작성

각 항목은 다음 넷을 갖춘다.

- **날짜** — 그 주 안의 발생일과 요일. 여러 날에 걸치면 범위로 쓴다. 발생일은 사건이 일어난 곳의 날짜로, 기사에 적힌 그대로 쓴다. 주 경계에 걸린 사안만 KST 로 따져 어느 주에 드는지 정한다.
- **무슨 일** — 사실 관계를 쓴다. 수치는 원문 그대로 쓰고, 출처끼리 다르면 어느 쪽인지 밝힌다. **어느 매체가 보도했는지는 쓰지 않는다.**
- **왜 중요한가** — 맥락과 파급. 헤드라인의 반복이 아니어야 한다. 출처에 없는 해석은 그 주의 다른 사안과의 연결로만 한다.
- **출처** — **매체 이름과 링크만** 쓴다. 무엇에 대한 링크인지, 1차 출처인지 같은 부연을 달지 않는다. 예외 하나는 아래에 있다.

**날짜순으로 늘어놓지 않는다.** 시점은 `날짜` 필드가 이미 답한다. 본문을 "15일 …, 16일 …, 17일 …" 로 쓰면 같은 정보를 두 번 쓰는 데다, 읽는 사람이 다섯 문단을 다 읽고 나서야 무엇이 핵심인지 알게 된다. 그 주에 남은 결과를 먼저 쓰고 나머지를 갈래로 묶는다. 날짜는 **그 자체가 사실의 일부일 때만** 문장에 넣는다. 사퇴가 지명 20일 만이라는 것, 청원 답변이 요건을 넘긴 지 두 시간 만에 나왔다는 것이 그런 경우다.

**한 항목에 여러 사안을 담을 때는 사안별로 묶는다.** 지출과 복지 삭감과 고발이 한 항목에 들어가면 셋을 각각 한 문단으로 쓴다. 날짜로 섞으면 독자가 갈래를 스스로 다시 세워야 한다.

**본문이 서너 문장을 넘으면 문단을 나눈다.** 한 덩어리로 이어 붙이면 읽는 사람이 어디까지가 한 갈래인지 알 수 없다. 인물·사건·국면이 바뀌는 곳에서 끊고, 한 문단은 한 갈래만 담는다. 마크다운에서는 항목 안에 빈 줄을 넣고 다음 줄을 두 칸 들여 쓴다.

```markdown
- **무슨 일**: 첫 갈래를 여기에 쓴다.

  둘째 갈래는 빈 줄 뒤에 두 칸 들여 쓴다.
```

**"왜 중요한가"는 특히 엄격하게 쓴다.** 이 칸은 직접 쓰는 판단이라 뜻이 흐려지기 쉽다. 한 문장이 확인할 수 있는 사실이나 근거가 붙은 판단 하나를 담게 하고, 다음 유형을 쓰지 않는다.

- **무엇을 가리키는지 없는 말** — "사실상의 표준", "관전 지점", "새로운 국면". 누가 무엇을 어떻게 했는지로 바꿔 쓴다.
- **판단이 없는 말** — "눈에 띈다", "주목된다", "의미가 크다". 무엇과 비교해 어떻다는 것인지 쓰거나 문장을 지운다.
- **근거 없는 예측** — "규제 논의에서 인용될 것이다". 그 주의 자료로 확인할 수 없으면 쓰지 않는다.
- **만드는 과정 이야기** — "헤드라인에서 38회로 가장 많이 반복됐다", "수집 풀에 없었다". 반복도는 무엇을 실을지 정하려고 우리가 잰 값이고, 독자에게는 그 사안이 왜 중요한지에 대한 답이 아니다. 중요도는 사안 자체로 쓴다.
- **비유** — 10절의 문체 규칙이 여기에도 그대로 적용된다.

**본문에는 매체를 쓰지 않는다.** "Axios에 따르면", "~로 보도됐다" 같은 말은 빼고 사실만 남긴다. 어디서 왔는지는 출처 줄이 답한다. 모든 항목의 모든 문장이 어차피 보도에서 온 것이라, 일부에만 붙이면 나머지는 출처가 없는 말처럼 보인다.

말한 주체를 밝히는 것은 다르다. "준비단은 청탁이 아니라고 반박했다" 처럼 **사건 당사자**가 한 말은 사실 관계의 일부이므로 그대로 쓴다.

**출처끼리는 `/` 로 나눈다.** 가운뎃점은 매체 이름 안에도 쓰여서 어디까지가 한 출처인지 흐려진다.

**순서는 1차 출처 → 주요 매체 → 보조 매체다.** 층 안에서는 쓴 순서를 그대로 둔다. 7절이 주요와 보조를 정하고, 그 표에 없는 이름은 발표 주체의 1차 출처다. 순서가 고정되면 첫 이름만 보고도 근거가 어느 층에서 왔는지 알 수 있다. 이 순서가 나타내는 것은 매체의 층이다. 보조 매체가 핵심 수치를 유일하게 실었더라도 뒤에 온다.

**같은 매체를 여러 번 인용하면 그냥 여러 번 쓴다.** `[CNN](url1) / [CNN](url2)` 이다. 구분할 키워드를 지어내지 않는다. 빌드가 이름을 한 번만 내고 링크마다 번호를 붙여 `CNN 1 2` 로 보여 준다. 위키백과가 여러 번 인용된 출처를 묶는 방식과 같다.

출처 라벨에 부연을 다는 경우는 하나뿐이다.

- **링크 대상이 위키백과면** 그 항목이 인용한 매체를 앞에 쓰고 괄호로 밝힌다. `The Guardian (Wikipedia)`. 매체명만 쓰면 링크 대상과 어긋나고, `Wikipedia` 만 쓰면 실제 취재처가 가려진다. 한 링크에 매체 하나만 쓴다.

제목에는 날짜를 넣지 않는다. 날짜는 별도 필드로 두어 화면에서 작게 표시된다.

분야별 건수는 사이트 머리말이 이미 밝히므로 화면에서 반복하지 않는다. 5건이 아닌 주차에만 건수가 드러난다.

### 12. 분야 도입 문단

세 분야 **모두** 첫 항목 앞에 도입 문단을 한 단락 둔다. 한 분야만 있고 다른 분야엔 없으면 안 된다.

**이 분야에서 무슨 일이 있었는지를 사건 이름으로 쓴다.** 도입만 읽어도 그 주에 무엇이 있었는지 알 수 있어야 한다.

- 1번 사안을 먼저 한 문장으로 쓴다. 나머지는 사건 이름으로 한두 문장에 묶는다. 항목의 요약을 다시 늘어놓지 않는다.
- 몇 건이 어떤 성격인지 같은 **구성 설명은 쓰지 않는다.** "다섯 건의 성격이 서로 다르다", "앞의 둘은 … 뒤의 셋은 …" 은 사건을 하나도 알려 주지 않는다.
- 공통점이 실제로 있으면 쓰고, 없으면 찾지 않는다. 억지로 엮지 않는다.

### 13. 콘텐츠 파일 작성

`content/week/<WEEK>.md`에 저장한다. 이 마크다운이 원본이고 HTML은 여기서 생성된다. 분기호와 연간호도 이 파일들을 읽어 만든다.

```markdown
---
week: 2026-W36
period_start: 2026-08-31
period_end: 2026-09-06
---

## 국내

(다섯 건이 어떤 성격인지 한 단락)

### 1. 제목은 한 줄로, 날짜 없이

- **날짜**: 9월 1일 (화)
- **무슨 일**: …
- **왜 중요한가**: …
- **출처**: [매체](url) / [매체](url)

## 해외

## AI
```

- 프론트매터는 평면 `key: value`만 쓴다. 건수는 적지 않는다. 빌드가 본문에서 센다.
- 섹션 제목은 `## 국내`, `## 해외`, `## AI` 셋으로 고정하고, 각 섹션은 도입 문단으로 시작한다.
- "이번 주", "최근" 같은 상대 표기는 제목에도 본문에도 쓰지 않는다.

### 14. 점검과 발행

**발행 전에 기계 검사를 돌린다.** [`QUALITY_CHECKS.md`](QUALITY_CHECKS.md) 3절이 검사 명령을 담는다. 대상 파일을 `W` 로 잡고 3절을 처음부터 끝까지 실행한다.

```bash
W=content/week/<WEEK>.md
```

**항목을 골라 돌리지 않는다.** 검사는 계속 늘어나므로 여기에 목록을 두면 그 목록만 낡는다. 걸린 것을 고치고 다시 돌려 빈 결과를 확인한 뒤 빌드한다.

**실행 기록을 남긴다.** 푸시 직전에 이 세션의 대화 기록으로 비용·시간·모델과 읽은 헤드라인 수를 계산해 `data/runs/<WEEK>.json` 에 쓴다. 발행물과 같은 커밋에 넣는다.

```bash
node scripts/record-run.mjs <WEEK>
```

- 기록한 뒤의 푸시와 확인은 빠진다. 한 호에 1% 미만이다.
- 백필은 한 호를 한 세션에서 만든다. 세션 전체가 그 호의 기록이 된다.

```bash
npm ci && npm run build
git add content/week/<WEEK>.md data/runs/
git commit -m "Publish <WEEK> (<MON>~<SUN>)"
git push origin main
```

- 이 저장소는 `main` 에 직접 발행한다. 브랜치를 따거나 풀 리퀘스트를 만들지 않는다.
- `site/`는 빌드 산출물이라 커밋하지 않는다. CI가 푸시마다 같은 빌드를 돌려 배포한다.
- 대량 수집과 푸시를 겹치지 않게 한다. 원문을 수백 건 받는 중에 푸시하면 게이트웨이 타임아웃으로 끊긴다.
- 푸시 뒤 CI 성공을 확인한다. 실패하면 로그를 읽고 원인을 남긴다.
- 오류를 발견하면 본문을 고친다. 무엇을 언제 고쳤는지는 git 이력에 남는다.

**배포된 페이지를 받아 본다.** CI 성공은 빌드가 끝났다는 뜻이지 페이지가 제대로 나왔다는 뜻이 아니다.

```bash
SITE=https://yg-moon.github.io/ai-weekly-news
curl -s "$SITE/week/<WEEK>/" -o /tmp/pub.html -w '응답: %{http_code}\n'
echo "항목: $(grep -c '<article class="item"' /tmp/pub.html)건"
echo "목록: $(curl -s "$SITE/" | grep -c "week/<WEEK>/")건"
```

응답 200, 항목 15건, 목록 1건이어야 한다. 하나라도 다르면 배포가 아직 안 끝났거나 빌드가 그 주차를 빠뜨린 것이다. 잠시 뒤 다시 보고, 그래도 같으면 CI 로그를 읽는다.

### 15. 분기말이면 이어서 분기호

**방금 발행한 주차가 분기의 마지막 주면** [`RUNBOOK_QUARTERLY.md`](RUNBOOK_QUARTERLY.md) 를 읽고 그 절차를 이어서 수행한다. 1절에서 주간호 작성을 건너뛴 경우에도 이 판정은 한다.

분기말 주차는 **13·26·39 그리고 그 해의 마지막 주**다. 마지막 주차는 해마다 52 또는 53이므로 고정해 쓰지 않고 아래로 구한다.

```bash
Y=${WEEK%%-*}                       # 예: 2026
LAST=$(date -d "$Y-12-28" +%V)      # 그 해의 마지막 ISO 주차. 2026 이면 53
```

- 판정 기준은 **발행한 주차**다. W13 주간호는 W14 월요일에 발행되므로, 오늘 날짜로 판정하면 분기의 마지막 입력이 갖춰지기 전에 돈다.
- `content/quarter/<분기>.md` 가 이미 있으면 그 분기는 만들어진 것이다. 덮어쓰지 않는다.
- 마지막 주차는 4분기말이면서 연말이다. 분기호를 먼저 만들고, 분기 런북 9절에서 연간 런북으로 이어진다.

## 제목과 경로 규약

| 대상 | 형식 | 예 |
|---|---|---|
| 콘텐츠 파일 | `content/week/<ISO주차>.md` | `content/week/2026-W36.md` |
| 사이트 경로 | `/week/<ISO주차>/` | `/week/2026-W36/` |
| 페이지 제목 | `<ISO주차> 주간 브리핑 (<기간>)` | `2026-W36 주간 브리핑 (8월 31일–9월 6일)` |

분기호와 연간호도 같은 규칙을 따른다.

| 대상 | 형식 | 예 |
|---|---|---|
| 분기 콘텐츠 | `content/quarter/<ISO연도>-Q<분기>.md` | `content/quarter/2026-Q1.md` |
| 분기 사이트 경로 | `/quarter/<ISO연도>-Q<분기>/` | `/quarter/2026-Q1/` |
| 연간 콘텐츠 | `content/year/<ISO연도>.md` | `content/year/2026.md` |
| 연간 사이트 경로 | `/year/<ISO연도>/` | `/year/2026/` |

목록은 종류가 아니라 기간으로 나뉜다. 발행물 자체의 경로와는 별개다.

| 대상 | 형식 | 예 |
|---|---|---|
| 분기 목록 경로 | `/<ISO연도>/Q<분기>/` | `/2026/Q3/` |
| 홈 | 가장 나중 분기 목록과 같은 화면 | `/` |

경로에 줄임말을 쓰지 않는다. 연도는 ISO 연도이며, 2026-W53 이 2027년 1월 3일에 끝나도 그 주는 2026년에 속한다.

## 플랫폼별 실행

절차 자체는 위가 전부다. 아래는 스케줄러를 거는 방법만 다룬다.

### 공통

- 스케줄: 크론 `0 23 * * 0` (UTC) = **월요일 08:00 KST**. KST는 일광절약시간이 없어 연중 고정이다.
- 실제 발화는 몇 분 늦는다. 서버가 루틴마다 고정 오프셋을 줘서 한 시각에 몰리지 않게 한다. 이 저장소의 루틴은 08:03 KST 다.
- 매 실행은 이전 실행과 문맥을 공유하지 않는 새 세션이어야 한다. 주간호끼리 섞이면 안 된다.
- 실행 세션에 주는 지시는 저장소를 받아 `AGENTS.md` 를 따르라는 포인터와 대상 주차 지정만 담는다. 사양은 저장소 문서가 가진다.

### Claude Code (현재 사용 중)

`create_trigger` 도구로 등록한다. 프롬프트는 [`ROUTINE.md`](ROUTINE.md) 에 있다.

| 필드 | 값 |
|---|---|
| `name` | `ai-weekly-news 주간 발행` |
| `cron_expression` | `0 23 * * 0` |
| `create_new_session_on_fire` | `true` |
| `notifications` | `{"push": true}` |
| `initiation` | `human_request` |
| `model` | `claude-opus-5-5` |

**루틴에 저장소를 등록해야 한다.** 등록 자리는 claude.ai/code/routines 의 편집 화면 "Select repositories" 다. `create_trigger` 도구에는 저장소 필드가 없어서 그 경로로 만든 루틴은 저장소가 비어 있다. 모델도 필드가 없어 만든 뒤 `update_trigger` 로 넣는다.

**저장소가 비면 읽기는 되고 쓰기가 막힌다.** 공개 저장소라 `git clone` 은 익명으로 한 번에 되지만, 푸시는 프록시가 자격 증명 주입을 거부한다.

```
remote: access denied by the git proxy: yg-moon/ai-weekly-news is not in
this session's authorized repository set
fatal: ... The requested URL returned error: 403
```

`credential.interactive false` 라 프롬프트 없이 그대로 실패한다. 수집과 집필을 다 마친 뒤 마지막 단계에서 끊긴다.

**MCP 도구는 저장소를 등록한 뒤에 생긴다.** 등록 전에 발화한 세션에는 `mcp__` 로 시작하는 도구가 하나도 없었고, 등록 뒤에 발화한 세션은 `mcp__github__` 로 브랜치와 워크플로 실행을 읽었다. 14절의 CI 확인을 여기서 한다. 저장소를 붙이는 `add_repo` 는 등록 뒤에도 없으므로 등록 자체는 루틴 편집 화면에서 한다.

**알림은 `PushNotification` 도구로 보낸다.** 새 세션 방식에서만 받는다.

**발화 페이로드는 프롬프트가 받겠다고 한 것만 전달된다.** 페이로드는 데이터로 취급되어, 세션은 루틴 프롬프트가 시키는 일만 한다. `ROUTINE.md` 프롬프트의 3번 줄이 주차 지정 하나를 받는다.

**`main` 에 직접 푸시가 통과한다.** 2026-09-17 확인이다. `main` 으로 미는 것과 `claude/` 브랜치를 새로 만드는 것이 둘 다 dry-run 을 통과했고, `main` 의 보호 설정은 꺼져 있다. 루틴이 세션에 `claude/` 접두 브랜치를 주더라도 14절대로 `main` 에서 작업하면 된다.

푸시는 그래도 추가 검사를 받는다. 보호 브랜치가 되거나, 그 브랜치에서 남이 연 풀 리퀘스트가 있거나, 남이 쓴 커밋이 있으면 거부된다.

**환경은 이 저장소로 수집이 되는 것을 확인한 곳을 쓴다.** 기본 환경의 네트워크 정책은 허용 목록 방식이라 네이버·위키백과 같은 수집처가 막힐 수 있다.

### 다른 플랫폼

- GitHub Actions `schedule` 로도 같은 크론을 걸 수 있다. 다만 수집에 웹 검색과 모델 호출이 필요하므로 API 키가 필요하다.
- 어떤 플랫폼이든 위 "공통"의 세 조건(크론, 새 세션, 포인터만 담은 프롬프트)만 만족하면 된다.
