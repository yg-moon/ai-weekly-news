# INTENT

이 문서는 **무엇을 왜 만드는가**를 담는다. 매주 어떻게 만드는지는 [`RUNBOOK.md`](RUNBOOK.md)가 담당하며, 두 문서는 같은 내용을 두 번 적지 않는다.

변경 빈도가 낮은 문서다. 실행 절차를 다듬는 일로는 이 문서를 건드리지 않는다.

## 대상과 범위

- 대상은 지난 한 주에 실제로 있었던 일이며, 지금 시점의 최신 속보가 아니다.
- 주의 경계는 ISO 8601 주를 따른다. 월요일에 시작해 일요일에 끝난다.
- 분야는 국내·해외·AI 셋이며 **각 5건으로 고정한다**. 주차끼리 비교가 되어야 월간·연간 인사이트가 성립하므로 건수는 흔들지 않는다.
- 세 분야는 각각 따로 고민한다. 하나의 방식으로 뭉뚱그려 처리하지 않는다.

## 목표

- 접근 가능한 정적 사이트를 GitHub Pages로 발행하고, 모바일과 데스크톱을 모두 지원한다.
- 주간호가 쌓여 월간 인사이트가 되고, 그것이 모여 연간 트렌드로 이어지게 한다.
- 분기·반기 단위를 둘지는 주간호가 충분히 쌓인 뒤 실제 필요를 보고 결정한다.

## 품질 기준

- 싣는 모든 사실은 기사 원문에서 확인한 것이어야 한다. 검색 결과 요약만 보고 쓰지 않는다.
- 복수의 독립 매체 보도를 원칙으로 한다.
- 건수를 채우기 어려울 때 양보하는 것은 **출처의 개수**이지 사실의 확실성이 아니다. 출처가 약한 항목은 그 사실을 화면에 표시한다.
- 억지 부리지 않는다. 안 되는 건 안 된다고 말하고, 한계를 감추거나 결과를 그럴듯하게 포장하지 않는다.
- 헤드라인 나열이 아니라 요약과 맥락을 함께 싣는다. "무슨 일이 있었는지"와 "왜 중요한지"가 모두 있어야 한다.
- 수집 기준과 선별 방식은 고정이 아니라 계속 다듬어 가는 대상이다.

## 결과물

- 웹페이지 형태로 본다.
- 매주 새로 쌓이며 덮어쓰지 않는다. 지난 주차를 언제든 되짚어 볼 수 있어야 한다.
- 제목만 봐도 언제 내용인지 식별된다. 시점이 모호한 표기는 쓰지 않는다.
- 발행이 완료되면 푸시 알림을 받는다.

## 기술 제약

- 버전 관리와 되돌리기가 가능해야 한다.
- 특정 AI 제품에 종속되지 않는다. 어떤 에이전트가 이어받아도, 사람이 수동으로 돌려도 같은 결과가 나와야 한다.
- 다음 프로젝트에 범용적으로 재사용할 수 있어야 한다.
- 사용자는 개발자이므로 git·CI·코드의 기술적 복잡도는 제약이 아니다.

## AI에게 위임한 것

- 어떤 매체를 쓸지. 단 품질 기준을 만족하는 범위 안에서다.
- 페이지 디자인과 데이터 구조.
- 국내 항목의 분야 배분. 결정은 아래 표에 있다.

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 발행 시점 | 월요일 오전 8시 (KST) | ISO 주가 완전히 닫힌 직후이며, 금요일 미국 시장·발표까지 포함된다 |
| 주 경계 | ISO 8601 주 (월요일~일요일) | 표준 주차 표기를 쓰면 제목의 시점 모호성이 자동으로 사라진다 |
| 건수 | 분야별 5건 고정 | 주차 간 비교 가능성이 축적의 전제다. 부족하면 출처 기준을 양보하고 건수는 지킨다 |
| 국내 배분 | 고정 비율 없이 중요도순 | 산업·경제와 정치·사회를 미리 나누면 그 주의 실제 무게와 어긋난다 |
| 저장소 공개 | public | 무료 계정에서 GitHub Pages는 public 저장소에서만 발행된다 |
| 발행 방식 | Pages 소스를 GitHub Actions 로 | 빌드를 직접 소유해 실패 로그를 전부 볼 수 있고, 워크플로와 스크립트는 다른 호스팅으로 그대로 옮길 수 있다 |
| 빌드 | `content/` 마크다운을 Node 스크립트로 `site/` 에 생성. 산출물은 커밋하지 않는다 | 원본이 마크다운이라 월간·연간이 파싱 없이 읽는다. 세션이 매주 HTML을 손으로 쓰면 인덱스와 레이아웃이 흐트러진다 |

## 아직 열린 항목

- 분기·반기 단위 인사이트를 둘 것인가.
- 월간·연간 인사이트를 어떤 방식으로 생성할 것인가.
