# RUNBOOK

매주 무엇을 어떻게 실행하는가의 유일한 기준이다. 스케줄러에 저장된 프롬프트는 이 문서를 가리키는 포인터일 뿐이며, 둘이 어긋나면 이 문서가 맞다.

절차 본문은 플랫폼에 중립적으로 쓴다. 특정 제품에서만 되는 것은 맨 아래 "플랫폼별 실행"에 모은다.

## 왜 이 문서가 기준인가

- 스케줄러에 저장된 프롬프트는 보통 그 서비스의 서버에 있어 git 밖이다. 거기에 사양을 쓰면 버전 관리도 되돌리기도 안 된다.
- 프롬프트는 짧은 포인터로 고정하고 실제 사양은 전부 이 파일에 둔다. 절차를 바꿀 때는 이 파일만 고친다.

## 실행 절차

### 1. 대상 주 확정

대상은 **직전에 완결된 ISO 주(월요일부터 일요일까지)**다. 실행 환경이 UTC라도 반드시 KST로 계산한다. 아래 명령은 어느 요일에 실행해도 맞다. 일요일 밤에 돌리면 아직 안 끝난 이번 주가 아니라 지난주가 나온다.

```bash
SUN=$(TZ=Asia/Seoul date -d 'last sunday' '+%Y-%m-%d')    # 대상 주 일요일
MON=$(TZ=Asia/Seoul date -d "$SUN - 6 days" '+%Y-%m-%d')  # 대상 주 월요일
WEEK=$(date -d "$MON" '+%G-W%V')                          # 예: 2026-W36
```

- `%G-W%V`는 ISO 연도와 주차라 연말 경계에서도 어긋나지 않는다. 2027년 1월 4일에 실행하면 `2026-W53`이 나온다. `%Y`를 쓰지 않는다.
- GNU date에서 `'2026-09-13 23:00 - 7 days'`처럼 시각 뒤에 `-`를 쓰면 시간대 오프셋으로 오독한다. 상대 표현은 위처럼 쓴다.
- `content/week/<WEEK>.md`가 이미 있으면 그 주는 발행된 것이다. 덮어쓰지 말고 종료한다.

### 2. 수집 방법

**웹 검색으로 후보를 찾고, 원문을 직접 받아 대조한다.** 두 단계를 모두 거친다.

- 검색 도구가 돌려주는 산문 요약은 생성된 텍스트이지 기사가 아니다. 후보를 찾는 데만 쓰고 사실의 근거로 삼지 않는다.
- 후보가 정해지면 기사 URL에서 본문과 발행일을 받아 대조한다. 수치·날짜·인용은 원문에서 확인한 것만 쓴다.

```bash
node scripts/read-article.mjs <URL>   # 발행일(article:published_time)과 본문 텍스트
```

- 발행일이 대상 주 밖이면 그 사안의 근거로 쓰지 않는다. 배경 설명에만 쓰고 그 사실을 밝힌다.
- 원문을 받을 수 없는 매체는 쓰지 않는다. 검색 요약만으로 항목을 쓰지 않는다.

### 3. 매체

국내 사안은 **한국어 원문을 우선한다.** 번역을 거치지 않아 표현과 수치가 정확하고, 영문판에 없는 사안이 많다.

| 구분 | 매체 |
|---|---|
| 국내 · 검색과 원문 모두 가능 | `newsis.com` `edaily.co.kr` `khan.co.kr` `hankyung.com` `sedaily.com` `pressian.com` `ohmynews.com` `news.sbs.co.kr` `etnews.com` `zdnet.co.kr` |
| 국내 · 검색은 막히고 원문은 가능 | `yna.co.kr` `chosun.com` `joongang.co.kr` `donga.com` `hani.co.kr` `mk.co.kr` |
| 국내 · 영문판 | `koreaherald.com` `koreatimes.co.kr` `koreajoongangdaily.joins.com` `en.sedaily.com` `en.yna.co.kr` |
| 해외 | `npr.org` `cnn.com` `aljazeera.com` `washingtonpost.com` `france24.com` `axios.com` `cnbc.com` |
| AI | 위 해외 매체와 `techcrunch.com` `bloomberg.com` `venturebeat.com`, 그리고 발표 주체의 1차 출처 |

- 검색이 막힌 매체를 `allowed_domains` 같은 필터에 넣으면 호출 전체가 실패한다. 넣지 않는다. 다만 다른 경로로 URL을 알면 원문 받기는 되므로 대조에는 쓸 수 있다.
- 목록에 없는 매체를 시도해 보는 것은 좋다. 새로 확인되면 이 표를 갱신한다.

### 4. 후보 풀 만들기

세 분야를 **각각 따로** 수행한다. 한 번의 검색으로 15건을 뽑지 않는다.

**검색어가 결과를 결정한다.** 경제 용어로만 검색하면 경제 뉴스만 후보가 되고, 순위를 아무리 정교하게 매겨도 후보에 없던 사안은 살아나지 않는다. 그래서 순위를 매기기 전에 아래 영역을 각각 최소 한 번씩 검색한다.

| 분야 | 훑을 영역 |
|---|---|
| 국내 | 정치·국회 / 경제·산업 / 사회·사건사고 / 외교·안보 / 노동·복지 / 과학기술·환경 |
| 해외 | 분쟁·안보 / 정치·선거 / 경제·시장 / 재난·기후 / 사회·인권 / 과학기술 |
| AI | 모델·제품 / 정책·규제 / 산업·자본 / 연구 / 안전·사회영향 |

- 영역마다 후보가 나오지 않아도 된다. 검색을 했는지가 기준이다.
- 최종 5건 중 한 영역이 3건 이상을 차지하면, 그것이 그 주의 실제 무게인지 검색이 치우친 것인지 다시 확인한다.

### 5. 게이트

중요도를 재기 전에 거른다. 하나라도 어기면 후보에서 뺀다.

- 그 주에 실제로 벌어진 일인가. 예고·전망·분석 기사는 사안이 아니다. 주 밖의 사안은 그 주에 후속 조치가 있을 때 그 후속을 싣는다.
- 원문으로 사실을 확인했는가. 검색 요약만 보고 통과시키지 않는다.
- 이미 고른 항목과 같은 사안이 아닌가. 같은 원인에서 나온 여러 결과는 하나로 묶는다.

### 6. 순위

게이트를 통과한 후보를 아래 넷에 무게를 두어 비교한다. 앞의 것이 더 무겁다.

1. **되돌리기 어려움** — 인명 피해와 집행된 결정이 가장 무겁다. 합의와 발표가 그다음이고, 검토·발언·전망이 가장 가볍다.
2. **영향의 범위와 깊이** — 몇 명에게 닿는지와 그 사람들의 삶을 얼마나 바꾸는지를 함께 본다. 범위가 좁아도 깊이가 절대적이면 무겁다.
3. **축적 가치** — 1년 뒤 월간·연간 정리에서 다시 볼 사안인가. 추세선 위의 점이 되는가.
4. **독자 근접성** — 한국 독자의 생활·일·자산에 닿는가. 해외 항목도 한국에 미치는 영향을 함께 본다.

**보도 매체의 수는 중요도 지표가 아니다.** 여러 매체가 다뤘다는 것은 검증이 쉽다는 뜻이지 그 사안이 더 중요하다는 뜻이 아니다. 순위가 팽팽할 때 마지막 판단 근거로만 쓴다.

정한 순서대로 번호를 매긴다. 1번이 그 주에 가장 무거운 사안이다. 시간순으로 늘어놓지 않는다.

### 7. 작업 순서를 지킨다

후보 풀 → 게이트 → 순위 → 항목 작성 → **마지막에** 도입 문단.

- 도입 문단을 쓰려고 항목을 바꾸지 않는다. 다섯 건에 공통점이 없으면 공통점이 없다고 쓴다.
- 하나의 주제에 맞춰 다섯 건을 고르는 것이 이 절차에서 가장 피해야 할 실패다. 주제는 결과이지 목표가 아니다.

### 8. 건수는 15건으로 고정한다

**세 분야 모두 5건을 채운다.** 주차끼리 비교가 되어야 월간·연간 인사이트가 성립하므로 건수는 흔들지 않는다.

채우기 어려울 때 양보하는 것은 **출처의 개수**이지 사실의 확실성이 아니다.

- 복수의 독립 매체 보도를 원칙으로 한다.
- 단일 매체 보도뿐이면 싣되, 그 항목 출처 끝에 `(단일 매체)`를 붙인다.
- 발표 주체의 1차 출처는 독립 매체로 세지 않는다. 1차 출처와 독립 매체 1곳이면 `(단일 매체 + 1차 출처)`로 밝힌다.
- 어느 경우에도 **원문 대조는 건너뛰지 않는다**. 출처가 하나여도 그 하나는 반드시 읽는다.

### 9. 문체

읽는 사람은 인상이 아니라 사실을 알고 싶어 한다. 멋있게 들리는 문장보다 한 번에 이해되는 문장을 쓴다. 이것은 취향이 아니라 품질 기준이다.

- 비유를 기본값으로 쓰지 않는다. 사실을 그대로 말하는 동사가 있으면 그것을 쓴다.
- 수치나 고유명사로 바꿀 수 있으면 그렇게 한다. "증시를 흔들었다"보다 "코스피가 3% 내렸다"가 낫다.
- 비유는 한 항목에 최대 하나다. 도입 문단과 "왜 중요한가"에 연달아 쓰지 않는다.
- 자주 새어 나오는 표현이다. 쓰기 전에 사실로 바꿀 수 있는지 확인한다.

  관통하다 · 쏠리다 · 흔들다 · 겨누다 · 가르다 · 맞물리다 · 굳어지다 · 축을 재편하다 · 한 몸이다 · 현실화되다 · 짚다 · 지평을 열다 · 신호탄 · 분수령

- 한 문장에 주장 하나만 담는다. 접속으로 길게 잇지 않는다.
- 쓴 뒤 소리 내어 읽어 본다. 무슨 뜻인지 한 번에 안 들어오면 고친다.

### 10. 항목 작성

각 항목은 다음 넷을 갖춘다.

- **날짜** — 그 주 안의 발생일과 요일. 여러 날에 걸치면 범위로 쓴다.
- **무슨 일** — 사실 관계를 서너 문장으로. 수치는 원문 그대로 쓰고, 출처끼리 다르면 어느 쪽인지 밝힌다.
- **왜 중요한가** — 맥락과 파급. 헤드라인의 반복이 아니어야 한다. 출처에 없는 해석은 그 주의 다른 사안과의 연결로만 한다.
- **출처** — 매체명과 링크. 출처가 약하면 8절의 표기를 붙인다.

제목에는 날짜를 넣지 않는다. 날짜는 별도 필드로 두어 화면에서 작게 표시된다.

분야별 건수는 사이트 머리말이 이미 밝히므로 화면에서 반복하지 않는다. 5건이 아닌 주차에만 건수가 드러난다.

### 11. 분야 도입 문단

세 분야 **모두** 첫 항목 앞에 도입 문단을 한 단락 둔다. 한 분야만 있고 다른 분야엔 없으면 안 된다.

- 다섯 건이 어떤 성격인지 한두 문장으로 쓴다. 항목의 요약을 다시 늘어놓지 않는다.
- 공통점이 있으면 쓰고, 없으면 성격이 서로 다르다고 쓴다. 억지로 엮지 않는다.

### 12. 콘텐츠 파일 작성

`content/week/<WEEK>.md`에 저장한다. 이 마크다운이 원본이고 HTML은 여기서 생성된다. 월간·연간 인사이트도 이 파일들을 읽어 만든다.

```markdown
---
week: 2026-W36
period_start: 2026-08-31
period_end: 2026-09-06
published: 2026-09-14
domestic: 5
world: 5
ai: 5
---

## 국내

(다섯 건이 어떤 성격인지 한 단락)

### 1. 제목은 한 줄로, 날짜 없이

- **날짜**: 9월 1일 (화)
- **무슨 일**: …
- **왜 중요한가**: …
- **출처**: [매체 — 구분](url) · [매체](url)

## 해외

## AI
```

- 프론트매터는 평면 `key: value`만 쓴다. `domestic`·`world`·`ai`는 실은 건수이며 정상 실행에서는 항상 5다.
- 섹션 제목은 `## 국내`, `## 해외`, `## AI` 셋으로 고정하고, 각 섹션은 도입 문단으로 시작한다.
- "이번 주", "최근" 같은 상대 표기는 제목에도 본문에도 쓰지 않는다.

### 13. 빌드와 발행

```bash
npm ci && npm run build
git add content/week/<WEEK>.md
git commit -m "Publish <WEEK> (<MON>~<SUN>)"
git push origin main
```

- `site/`는 빌드 산출물이라 커밋하지 않는다. CI가 푸시마다 같은 빌드를 돌려 배포한다.
- 푸시 뒤 CI 성공을 확인하고 종료한다. 실패하면 로그를 읽고 원인을 남긴다.
- 발행된 주간호의 본문은 고치지 않는다. 오류는 파일 끝에 `## 정정` 절을 두고 날짜와 함께 덧붙인다.

## 제목과 경로 규약

| 대상 | 형식 | 예 |
|---|---|---|
| 콘텐츠 파일 | `content/week/<ISO주차>.md` | `content/week/2026-W36.md` |
| 사이트 경로 | `/week/<ISO주차>/` | `/week/2026-W36/` |
| 페이지 제목 | `<ISO주차> 주간 브리핑 (<기간>)` | `2026-W36 주간 브리핑 (8월 31일–9월 6일)` |

경로에 줄임말을 쓰지 않는다. 월간·연간을 얹을 때도 `content/month/`와 `/month/2026-09/`, `content/year/`와 `/year/2026/`으로 같은 규칙을 따른다.

## 플랫폼별 실행

절차 자체는 위가 전부다. 아래는 스케줄러를 거는 방법만 다룬다.

### 공통

- 스케줄: 크론 `0 23 * * 0` (UTC) = **월요일 08:00 KST**. KST는 일광절약시간이 없어 연중 고정이다.
- 매 실행은 이전 실행과 문맥을 공유하지 않는 새 세션이어야 한다. 주간호끼리 섞이면 안 된다.
- 실행 세션에 주는 지시는 아래 네 줄이면 충분하다. 이 이상을 프롬프트에 넣지 않는다.

```
yg-moon/ai-weekly-news 의 주간 브리핑을 발행한다.

1. 저장소를 클론한다.
2. docs/RUNBOOK.md 를 처음부터 끝까지 읽는다.
3. 그 문서의 절차를 그대로 수행한다. 사양의 기준은 이 프롬프트가 아니라 RUNBOOK.md 다.
4. 판단이 필요한 지점은 docs/INTENT.md 의 원칙을 따른다.
```

### Claude Code (현재 사용 중)

`create_trigger` 도구로 등록한다.

| 필드 | 값 |
|---|---|
| `name` | `ai-weekly-news 주간 발행` |
| `cron_expression` | `0 23 * * 0` |
| `create_new_session_on_fire` | `true` |
| `notifications` | `{"push": true}` |
| `initiation` | `human_request` |

- 클론 전에 `add_repo` 로 저장소를 세션에 붙여야 한다. 위 프롬프트 1번이 그 일이다.
- 푸시 알림은 새 세션 방식에서만 받는다.

### 다른 플랫폼

- GitHub Actions `schedule` 로도 같은 크론을 걸 수 있다. 다만 수집에 웹 검색과 모델 호출이 필요하므로 API 키가 필요하다.
- 어떤 플랫폼이든 위 "공통"의 세 조건(크론, 새 세션, 네 줄 프롬프트)만 만족하면 된다.

## 아직 검증되지 않은 것

- 스케줄러가 띄우는 새 세션에서 저장소 접근이 되는지.
- 푸시 알림이 실제로 도착하는지.
